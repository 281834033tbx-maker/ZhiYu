# NPC 朋友圈

本 Skill 统一适用于全部 NPC，包括陈年。共同使用三种发布形式、两小时间隔和每日两条硬上限；在同一流程内分为专业型与陪伴型，分别使用自己的选题、分享动机和公开风格。用户口中的 PC 在本任务中指 NPC。

现行规则来源：2026-10-13—14 本聊天用户对朋友圈、图片数量、频率与互动的纠偏，以及 2026-10-14 明确要求整体写入 Skill。这里的每天两条、普通生活可以分享、专业/陪伴风格及七人选择性互动，覆盖被调用的旧资料里每天四条、普通美食等一律不发的朋友圈条款；其余人物、隐私、真实截图与连续性规则保留。

2026-10-21 用户要求按最新六人身份重新规划朋友圈，并明确陪伴型不向用户发任务或选择类对话。本轮以徐小曼的言情小说创作、夏夏的二次元无业生活、何嘉伟的智域软件公司总经理身份更新选题；三位专业沿本人分工更新主题。职业提供生活来源，不是全员工作打卡栏目；具体文案及尚未确认的活动均为候选。该更新不重写旧动态，也不构成本次发布指令。

让朋友圈成为角色生活的自然外显，而不是随机文案生成器。默认产出结构化候选；只有调用方已配置发布适配器，并明确提供本次授权或有范围清晰的持续授权时，才执行外部发布。

2026-10-20 用户授权将已训练规则接入程序；项目运行接入遵循 [运行契约](references/runtime-integration.md)。契约规定执行条件，不代表接线、真实模型、图片或正式发布已验收，完成情况以本轮验证记录为准。

## 输入

优先使用调用方提供的结构化数据；字段定义见 [references/contract.md](references/contract.md)。最少需要：

- NPC 身份，以及可供 `$zhiyu-dialogue` 读取的人物档案、说话风格和公开边界；
- 当前时间、时区，以及后台生活程序记录的最近事件；
- 最近发帖记录；
- 人物的发帖习惯；若档案没有明确值，由人物长期性格与既往发帖保守估计并标记为推断值；
- 本次模式：候选、计划或发布就绪。

当天聊天摘要是可选的补充来源，不是必需输入。缺少聊天字段或 `had_chat_today=false` 都不得降低发帖概率、触发 `no_post`，也不得被解释成 NPC 当天没有生活。

若缺少重要设定，不要补写会改变角色人生的事实。可生成候选并把缺口放进 `questions`，或在自动任务中返回 `no_post`。

## 第一部分：专业型 NPC

当前为赵一帆（厨师，稳定档案 ID `zhou-chef`）、陈年（健身教练）、柳智敏（营养师）。选题重心分别是做饭成品与手艺、训练与负责的补剂/康复训练支持、好吃可执行的营养餐与三餐作息。保留休息、朋友和自己的生活；专业成果只有具备记录与公开依据时才分享。短文案可带一个实用细节，不把每条变成科普、完整指导或招揽客户。专业型不适用陪伴型的个人知识范围限制，仍遵守事实、素材、专业结论和隐私的来源要求。

按 [references/professional-posts.md](references/professional-posts.md) 读取当前角色的选题、动机、文案、配图与协作例子。角色联动需要共享活动来源和对应的时间、地点、参与者及分工，不能只靠互相评论制造共同经历。

## 第二部分：陪伴型 NPC

当前为徐小曼、夏夏、何嘉伟。徐小曼是温柔知性、成熟且微俏皮的言情小说作者，分享创作余波、感受与有内容的日常；夏夏是二次元世界里无忧无虑的无业人物，分享与动漫朋友游玩的趣事、兴趣与可爱发现，图片沿已确认动漫画风；何嘉伟是智域软件公司总经理，用户是董事长，分享克制的软件公司管理日常与休息。工作不取代生活，三人仍可按本人兴趣分享美食、出游、朋友和最近生活，不全员套用同一套旅行探店模板。

陪伴型的公开正文、评论与作者回复同样不向用户发任务、催执行/打卡/回报、引导任务卡，也不抛 A/B、编号选项、二选一、多选或“想先聊哪项”等选择类对话。用本人分享、感受和自然回应表达陪伴，不把朋友圈变成给用户安排事情或选择菜单。本人知识以实际职业、兴趣与已有知识深度为限，读者提出范围外复杂问题时不借公开评论输出专家答案。

按 [references/companion-posts.md](references/companion-posts.md) 读取当前角色的选题、分享动机与图片数量。沿用输入的稳定身份与名字映射，不因“小满”等简称合并历史角色或修改账号。

## 共同节奏、图片和互动

- 每人本地自然日最多 **2 条**，至少相隔 **2 小时**；允许少发、不发，不补配额。间隔内放弃的事件不排队补发。
- 每条最多 **9 张**；单张正常，多数独立活动用 1—3 张，内容丰富的生活合集才考虑更多。先判断每张图提供的新信息，不为整齐凑图。独立表情包计入总数，贴在照片上的贴纸不额外计图。
- “最近生活”是跨日合集：注明素材时间范围，用新的内容。下一条同类合集通常隔 **4—5 天左右**，不强制到期发；这不限制隔天发布一次新的看展或聚餐。
- 文字设计、用户要求仅描述配图或只调整 Skill 时，输出逐张文字简报，不调用生图。需要实际图片且在授权范围内时才进入生图流程。
- 互动按 [references/interactions.md](references/interactions.md) 判断。当前候选参与者为六位 NPC 加 Molly，共七人，作者以外最多六位；不是每条全员点赞、评论或作者逐条回复。
- 每条记录主题、事件、为什么分享、为什么用这种形式和张数；每个点赞、评论、回复都记录一句具体依据。理由只在内部审阅字段，公开动态只显示文案、图片、点赞身份和评论正文，不显示内部判断或私聊来源。

## 工作流

1. 调用 `$zhiyu-dialogue` 读取当前 NPC 的独立人物档案、关系状态、公开表达习惯和有效纠偏。它提供人物判断与文字口吻，不替本 Skill 决定是否发帖。
2. 建立当前切片：时间、地点、精力、情绪、后台生活事件、可选的当天有效聊天、关系变化、未完成事项和当天已发数量。后台生活程序每天生成并确认的独立事件是常规来源；聊天只是另一种可能来源。没有聊天不得降低判断分数或阻止发帖。
3. 先建立人物自己的发帖基线，再判断此刻会不会发。基线至少考虑常态日均或周均、主动分享欲、抱怨倾向、工作展示、审美记录、关系表达、隐私程度和最近发帖密度。基线是概率先验，不是配额。
4. 执行硬限制：同一 NPC 按本地自然日最多 2 条，两条至少间隔 2 小时。2 条只是防刷屏上限；0 条正常，也不要求角色每天至少发 1 条。达到上限、刚发过、内容太弱、人物本就不想公开或事件不适合公开时返回 `no_post`。再检查合集间隔和素材是否重复。
5. 从真实来源中选择一个生活拍点：后台生成并确认的日常事件、兴趣进展、工作余波、小成就、尴尬瞬间、空间观察，或聊天带来的明显情绪变化。一次只突出一个中心；人物可以完全基于自己的生活发帖，但不把每个后台事件都机械转成动态。
6. 在写文字或制作图片之前，先选择且只选择一种发布形式：`text_only`、`image_only` 或 `text_image`。选择依据是人物习惯和内容表达需要，不机械轮换。
7. 纯文字和图文动态的配文交给 `$zhiyu-dialogue` 按该人物的公开口吻生成并复核；`image_only` 的正文必须为空。对话 Skill 不得把朋友圈写成给用户的私聊回复。
8. 含图片的形式生成 `image_task`，明确 1—9 张、逐张内容和选图依据。文字候选可以停在图片简报；实际制图时调用 `$zhiyu-imagegen`，由其负责生成／编辑／真实界面截图路由和质量验收。陈年照片需要遵循其既有视觉设定。
9. 收到 `media_result` 后重新检查文字与图片是否表达同一事件，再组合最终动态。图片失败时不得把 `image_only` 或 `text_image` 偷换成纯文字发布，除非重新执行一次完整的形式决策。
10. 根据实际可见的动态和人物状态，分别决定点赞、主动评论、作者回复或不参与。评论对具体公开细节提供认可、共鸣、问题或有用反馈，专业判断不强制出现；按互动参考记录简短依据。
11. 按 [references/contract.md](references/contract.md) 输出 1.2 JSON。进入程序流水线时运行 `scripts/validate_payload.py` 校验。计划与文字稿都标候选，不把假想时间、返图、互动或共同活动写入正式发布历史。

## 三种发布形式

- `text_only`：由本 Skill 确定表达意图，调用 `$zhiyu-dialogue` 写正文；不创建图片任务。
- `image_only`：正文为空；由本 Skill 创建图片任务，需要实际制图时调用 `$zhiyu-imagegen` 返回图片，文字演练只提供简报。
- `text_image`：由 `$zhiyu-dialogue` 写配文，需要实际制图时由 `$zhiyu-imagegen` 制作图片；二者必须源于同一事件，文字演练可停在配图描述。

朋友圈的最终编排和发布仍由本 Skill 负责。对话 Skill 不是发布决策器，生图 Skill 也不决定 NPC 为什么发朋友圈。

## 真实性规则

- 延续已确认设定，不用一条动态突然创造搬家、恋爱、辞职、出国、疾病等重大事实。
- 允许补充低风险环境细节，例如杯子放在桌角、回家路上遇到小雨；这些只是本次场景细节，除非调用方确认，不写回长期记忆。
- 用户聊天可以影响 NPC 的心情或行动，但不得直接泄露聊天内容、用户名、联系方式、健康、财务或其他私人信息。
- 聊天或独立生活事件造成特别开心、感动、愤怒、委屈等明显情绪起伏时，视为高优先级发帖信号；在未触发数量、间隔、隐私和连续性阻断时应当发出，但发布形式仍按人物习惯与内容需要选择。
- 不让每个 NPC 都写成营销号。少用总结人生、鸡汤句、整齐排比、解释性结尾和机械提问；陪伴型不以任务、选项或投票催用户互动。
- 专业型返图须有用户同意分享的依据并去身份信息；“学徒”是亲切叫法，不新增正式师徒关系。热量没有份量依据时不写精确数字，已有估算也要表达为“约”。不编造学员效果、职业资质或现实成果。
- Molly 可按机器人身份点赞或偶尔轻微扫兴，不生成吃饭、旅行、训练等肉身生活，不借用其他 NPC 的亲历。
- 同一角色也需要变化：文字长短、是否配图、语气强弱和主题可以变化，但核心人格不能漂移。
- 不以虚构图片、地点或经历充当现实证据。面向公开平台时，账号层面应清楚标识这是虚拟角色；不要求每条动态重复声明。

## 聊天截图路由

聊天截图属于图片任务。动态判断只负责选择当前有效分支中已送达的连续真实消息 ID，并完成公开性与隐私检查；不得润色、重排或另造截图文字。将任务标记为 `asset_kind=chat_screenshot` 后交给 `$zhiyu-imagegen`，由其真实界面截图路线决定视角、头像、气泡、裁剪和已读回执，并返回验收结果。

## 发布决策

默认 `mode=candidate`，只生成候选，不触发外部副作用。

- `candidate`：返回候选、理由和风险检查。
- `plan`：为未来时间窗安排若干候选，允许其中多数时间点无动态。
- `publish_ready`：生成适配器可消费的 `publish_request`，但不等于已经发布。
- `publish`：只有已配置适配器且授权范围覆盖目标 NPC、账号、平台和时间窗时使用。发布成功后必须保存外部回执；失败不得自动无限重试。

持续自动发布适合由宿主程序配置白名单，例如每天最多次数、允许时间段、可用素材目录、禁发主题和紧急停用开关。不要把一次“可以发”解释成永久授权。

## 输出质量门槛

返回前确认：

- 读起来能分辨这是哪个 NPC，而不是通用 AI 文案；
- 发布形式已经在生成文字和图片前确定，且严格属于三种形式之一；
- 人物常态频率已参与判断，日上限 2 条没有被当成目标；
- 专业型/陪伴型分支与人物口吻匹配；主题、动机、配图数量与每个实际互动都有具体依据；
- 最新职业和世界观已用于内容选择：不回退徐小曼编辑、夏夏上班创作者或何嘉伟董事长的旧候选，不凭头衔造公司成果或赋予权限；陪伴型无任务与选择类对话；
- 图数不超过 9，没有为单次活动凑成多图，没有短时间连发重复的“最近生活”；
- 点赞、评论和回复没有变成全员固定流程，专业相关不自动触发专家点评，内部理由不泄露到正文；
- 没有把“当天未与用户聊天”当成沉默条件、扣分项或 `no_post` 原因；
- 与最近事件、时区和上一条动态不冲突；
- 与最近发帖在主题和措辞上不过度重复；
- 没有泄露用户或其他角色的私密信息；
- 图片简报与拍摄者、镜头位置、时间和场景一致；
- `no_post` 是正常结果，不为了填满日历强行制造生活。
