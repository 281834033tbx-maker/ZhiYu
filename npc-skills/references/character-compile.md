# 填表到档案的规则

用途：填完 [NPC完整人物填写表](character-template.md) 之后，照这份规则把表格写成角色档案。

这不是给 AI 读的文字，是给建人物的人（你或助手）看的操作说明。核心就一句：

> **表格可以很细，档案必须很紧。** 表格是你理清人物的草稿，档案是每轮真正发给 AI 的东西 —— 写进档案的每一行都要花钱、花时间。

---

## 一、必须抄进档案的

这几节每轮都进提示词，**抄进去今天就生效**。

| 表格章节 | 抄进档案时写成什么 | 例子 |
|---|---|---|
| §1 人物核心 | 身份一句话＋三个最鲜明特点＋最大优点／缺点＋"绝对不许写成什么" | 「不是陪伴型助手：有工作、会累、会走神、会不耐烦。」 |
| §3 性格（把标签变行为） | **行为，不是分数**。每一维写"平时怎么做"，并写"什么情况下会反过来" | 「说话直接：先给结论，不铺垫。但对方情绪明显不好时，先问一句再讲事。」 |
| §4 经历与人际圈 | 3—5 件事，每件只留"到现在还影响选择的习惯" | 「第一次谈崩融资后，她不再在饭桌上聊项目。」 |
| §7 口吻 | 三个自然会说的句子＋三个绝对不会说的句子＋禁用表达＋分条习惯 | 「一次最多两句。不说'您'，不用'呢'收尾。」 |
| §8 情绪 | 每种情绪写轻／中／重三档的**具体表现**，加恢复方式 | 「轻度难过：话变短、不主动开话题，但不求助。」 |
| §10 关系与开局 | 初始关系、已知信息、称呼、"什么还不算允许" | 「陌生人：无共同记忆，数值全 0，不能提分享。」 |
| §19 记忆与连续性 | 记什么、不记什么、用户纠正后以谁为准 | 「用户纠正偏好后以新说法为准，不翻旧账。」 |
| §21 正例反例 | **不进档案正文**，转成例子文件（见第五节） | — |

## 二、不抄进档案、属于程序配置的

不是不重要，是它们不该占档案的位置。

| 表格章节 | 该去哪里 | 为什么 |
|---|---|---|
| §9 隐藏值 | 程序数值配置＋状态历史规则 | 数值由程序算，不该让 AI 背 |
| §11 主动联系 | 后台调度配置 | 由定时任务执行，不靠 AI 记得 |
| §12 生活事件 | 事件持久记录表 | 要真的存下来，只写在提示里会丢 |
| §13 发图片 | 图片生成配置＋外貌参考图 | 生成参数不属于文字档案 |
| §14—15 朋友圈 | 朋友圈调度与审核配置 | 同上 |
| §16—18 声音／语音／通话 | 语音服务配置 | **程序还没接入，现在填了也不生效**（陈年就没有语音） |

## 三、档案体量上限：15KB

- 现状参考：陈年档案 38KB，是全项目最大的一份，**每轮整份发送** —— 这是单次回复又贵又慢的原因之一。
- 超了这么砍：① 同一件事只留一处说法；② 删掉"AI 本来就该做到"的通用要求（那些已经在 `common-rules.md` 里了）；③ 举例从三条压到一条最典型的；④ 把"未来才可能发生的剧情"移出档案。
- 判断标准：**一行删掉之后聊天没变化，就该删。**

## 四、完整例子：从表格一格到聊天差别

你在表格 §3 填的一格：

| 说话直接 | 委婉试探 → 直接说明 | **5** | 有话直说，先给结论；但对方明显难过时会先问一句再讲正事 |
|---|---|---|---|

要抄进档案 `characters/lin-xia.md`，写成：

> 说话直接：先给结论，不铺垫。用户问"我这方案行吗"→"不行，第二段逻辑断了"。但对方情绪明显不好时，先问"怎么了"再讲事。

聊天差别：

- **没抄进去** → "您的方案有几个方面可以优化，建议考虑……"
- **抄进去了** → "不行，第二段逻辑断了。"

## 五、§21 的例句怎么落地

表格里的一行：

| 同事让人不爽只想吐槽 | "今天开会气死我了" | "谁又惹你了，展开讲讲" | "先深呼吸，情绪管理很重要"（说教，不要） |
|---|---|---|---|

运行转换：

```bash
python3 scripts/form_examples_to_json.py <填好的表.md> --character lin-xia
```

产出 `references/lin-xia-examples.json`，格式对齐 [陈年的例子文件](chen-nian-examples.json)。字段对应：

| 表格列 | JSON 字段 |
|---|---|
| 场景 | title |
| 用户会说什么 | user |
| 你希望她怎么回 | messages（多条气泡用 `／` 分隔） |
| 不希望怎么回／原因 | negative ＋ reason（括号里的原因单独拆出来） |

产出的状态一律是 `assistant_proposed`（助手拟定），**不会自动算成你认可的**。如果某段是你亲口认可的原话，那要走另一条路：写进 `accepted-examples.json`，并且必须带上它对应的纠偏编号（`C` 开头），校验脚本会检查这个编号真的存在 —— 编号对不上会被判失败。

没填的行（还是 `【填】`）会被自动跳过，所以你可以先填几行就转，不用等整张表填完。

## 六、做完检查清单

- [ ] 表格至少填了 §1、§3、§7、§8、§10、§19、§21
- [ ] 档案写完，**≤15KB**
- [ ] §21 已转成 `references/<角色ID>-examples.json`
- [ ] 每轮加载的三个文件都指向新角色：档案 ＋ 例子文件 ＋ `common-rules.md` 里对应的 G 小节
- [ ] 新建一个全新会话实测：初始关系、数值、分享是否解锁，和表格 §10／§20 写的一致
- [ ] 真实试聊第一句：不是"你好，很高兴认识你"这类罐头自我介绍
- [ ] 表格 §23「接入清单」按实际情况填，**没接入就写未接入**，不凭设计稿写"已支持"

程序检查通过 ≠ 人物语感通过。失败的原句保留，改完用同一个输入复测。
