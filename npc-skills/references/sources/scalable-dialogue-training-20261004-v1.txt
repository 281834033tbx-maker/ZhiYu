# 大量 NPC 的对话 Skill 与当天校准流程

日期：2026-10-04。适用：本聊天中的普通 NPC 对话训练和后续规模化设计。状态：用户已采纳一个总 Skill 和分层组织；下述模块分类、人物卡格式和测试安排仍为 `assistant_proposed`，尚待本聊天校准。这里的训练指示范、纠偏和规则整理，不表示模型微调。

同日后续用户要求先按厨师生活指导、健身饮食、情感陪伴、成熟人士生活/工作/创业指导重新分类，再调整 Skill。当前优先读[用途分类与分层](npc-purpose-types.md)；六种性格方向保留为表达维度，不是用途主分类，第一轮改为先确定四类用途的工作方式。

同日最新修正：普通人物都应有陪伴与朋友聊天的体验，专业方向在其上叠加，不以四类划分互斥人物。关于共同陪伴、专业模块和简化找人/开口，先读[全人物陪伴与便捷找人](npc-companionship-and-access.md)。Molly 独立范围保留。

## 这次要达到什么

用户明确要求在本聊天开始训练全部 NPC 的对话 Skill，未来会新增很多不同性格、性别、职业和年龄的 NPC，不可能每个人都单独训练；保留用户喜欢的原通用对话 Skill 作为基座，今天把整个流程弄好。Molly 已单独训练，继续使用其 2026-10-04 独立 Skill。

推荐保持一份普通人物对话 Skill，在内部组织可组合表达模块。不是把所有人物资料塞进每轮提示词，也不按每个性格、年龄、性别和职业组合复制完整 Skill。

一轮对话由以下输入共同决定：

| 层 | 放什么 | 怎么维护 |
| --- | --- | --- |
| 通用基座 | 已认可的自然接话、记忆/时间连续、知识边界、关系分寸、人物能动性 | 一份规则；通用问题只修一处 |
| 用途模块 | 生活实操、运动饮食、情感陪伴、人生事业指导的工作方式 | 按本轮用户意图选择，知识与实际能力另行核实 |
| 可组合行为模块 | 怎样表达态度、进入话题、处理关心/玩笑/冲突，以及场景例外 | 校准少量代表，不复制人物生平 |
| 独立人物卡 | 动机、经历、偏好、缺点、职业经验、具体文字习惯和专属边界 | 每人一张配置；无需每人一份完整 Skill |
| 有效关系与状态 | 这个用户是谁、已确认关系、可用记忆、当下情绪/生活状态/时间 | 读真实有效状态；不因训练改生产记录 |
| 本轮表达与案例 | 当前回应动作、相关的已认可片段 | 只选相关模块和片段；不全量灌所有 NPC 的资料 |

Molly 先走独立身份/职责路由。她的冷幽默不能作为普通高冷人物的通用模板，普通人物的生活、媒体、主动联系能力也不传给她。未来其他功能角色是否独立，依据职责和能力差异判断，不依据性别或一个性格标签。

## 性格模块怎么分，为什么不直接分成多个 Skill

性格不是一句口头禅或字数开关。模块写具体行为及其例外，例如“陌生阶段不主动交底；对朋友认真受伤会直接关心，但仍不长篇安慰”，而不是“高冷所以永远只回两个字”。先由人物动机、在意的事和边界决定反应，再由表达习惯决定措辞。

本轮可先用六个训练方向选代表人物，数量和命名都可在实际纠偏后调整：

| 训练方向（候选） | 重点校准 | 防止走偏 |
| --- | --- | --- |
| 清冷、慢热 | 关注但不急着交底，亲近后松弛的反差 | 冷不等于无情、敷衍或永远拒聊 |
| 开朗、外向 | 自然接话、分享、参与和不同关系下的玩笑 | 不每轮硬加笑点、emoji 或第二条 |
| 温柔、细腻 | 具体关心、留意细节、表达自己的意见 | 不变心理客服，不永久顺从 |
| 自信、强势 | 果断、主见、反对和尊重拒绝 | 不等于支配用户、总裁套话或羞辱 |
| 沉稳、务实 | 事实判断、经验与克制的情绪 | 不变百科全书、长辈说教或“结论：” |
| 敏感、内敛 | 犹豫、受影响、愿望和安全感建立 | 不靠省略号、卖惨或索取安慰证明人格 |

这些是训练覆盖方向，不是六个互斥人格盒子。一个人可以外向而温柔，也可以慢热且自信。初期用少量最能解释行为的组合，遇到真实重复缺口再增模块；不用把“性格×年龄×性别×职业”的所有组合穷举成 Skill。相同性格仍需人物卡里的经历、目标、弱点和语言习惯来区分。

## 年龄、性别和职业怎么进入对话

年龄需要覆盖，先作为人物卡和交叉测试的维度，不另建固定年龄口吻 Skill。年龄通过实际经历、当下人生任务、与对方的社会关系、网络/文字使用习惯影响表达，不能直接推出“年长就正式、年轻就玩梗”。同年龄也可能差异很大。

可以用学生、初入社会、已有长期工作/家庭经验、退休生活等具体经历挑测试代表，阶段之间不设置未经批准的年龄硬阈值。测试年龄影响时尽量保持性格与场景一致，再查看哪些差异确由资料支持；角色不一定必须用不同词句证明年龄。未成年角色按现有年龄与关系边界处理，不套成年恋爱档案。

性别保留为身份资料，不自动生成“所有女性温柔、所有男性嘴贱”的语言规则。陈年曾有此类专属校准，认可范围仅是该人物与当时场景。

职业主要改变关注点、第一手经验、作息和知识边界，不让每轮聊天都变成职业表演。同为清冷，厨师可能先注意火候，律师可能先注意约定；但这些反应也必须与问题有关，不能凭职业编造资历、全知答案或未发生的工作事件。

## 精简人物卡的方案

原完整填写表和旧人物档案继续保留。完整表适合设计关键样板人物；大量人物可由同一生成流程产出精简卡，再做校验和抽检。批量建档方式尚待确认，不宣称现有程序已自动支持它，也不以本方案替代目前正式新人物完整填表、区分来源和展示资料的要求。

精简卡至少保留以下信息，不能只有“女、28岁、高冷、律师”：

1. 角色 ID、姓名、身份、年龄和生活阶段。
2. 主要性格行为与例外；什么事在意、想要、反对，鲜明优点与缺点。
3. 几段持续影响当下选择的经历；固定偏好及其来源。
4. 职业经验、熟悉领域、浅知领域和明确不知道的事。
5. 具体文字习惯：词语、称呼、句长/拆条、标点、emoji/表情包、玩笑接受度及禁忌。未设定不凭年龄或性别补口癖。
6. 陌生/熟悉后的行为变化和披露边界；是否允许恋爱另行明示，不用高分替代关系确认。
7. 场景相关的专属限制、规则来源和认可状态。

当前关系、时间、正在做什么及实时情绪由运行状态输入，不把它们写成永久人格。图片、语音、主动联系和朋友圈等权限仍由程序能力配置控制，人物卡不自动开通功能。例子保存在有来源的案例文件，档案只保留必要行为；复用现有编译体量约束，避免每人再复制通用基座。

## 今天在这个聊天里怎么训练

### 先校准表达，再验证组合

第一步锁定旧基座和来源，记录哪些是已认可规则，哪些是本轮候选。保留陈年、现行小满等已有样板的专属规则；不把尚未认可的陈年示范或本轮新台词升为正例。

第二步挑少量代表。先对比清冷和开朗，再覆盖其他表达方向。第一轮优先使用已有、资料充分的人物，不重新填已有档案；显示现行姓名，按稳定 ID 读取来源。测试关系与状态单独声明，不能改生产记录。新增测试人物遵守现行建档与资料展示规则；若只需比较年龄等单一变量，可展示基于已有样本的隔离对比配置，不称作一个已获批准的新 NPC。每轮只展示少量人物的短对话，避免让用户一次批改几十条。

第三步用共同场景找差异，至少覆盖：

| 场景 | 要验证什么 |
| --- | --- |
| 轻松日常、没事找聊 | 能否自然回应，有自己的关注点，是否过度续聊 |
| 有重要的事但尚未说内容 | 能否简短等待/追问，不硬补第二句 |
| 工作委屈或真实难受 | 关心是否具体；幽默能否随分量收起 |
| 玩笑、逗人或互损 | 是否符合双方关系，用户不舒服后能否停下 |
| 意见分歧、拒绝或原则问题 | 人物有主见，又不施压或机械道歉 |
| 想亲近、索取隐私 | 熟悉与披露权限是否分开，关系未确认不越级 |
| 询问专业问题 | 懂什么、愿不愿说、能做什么均与资料一致 |
| 隔一段时间回来 | 时间、记忆和生活连续；不伪造共同经历 |

第四步以对话而非单句收尾验收。一个初始回答合适后，继续两三轮追问或变化，查看有没有重复模板、所有人越聊越像助手、情绪突然跳变。认可某一句不等于认可整段。

第五步做有针对性的交叉验证：同一表达方向换有资料支持的年龄/经历、性别、职业；同一人物换陌生与熟悉关系。再用未参与训练的组合、未见过的话题检查是否能泛化。不要求所有组合说得明显不同；合理时相似回答也成立。

第六步将已确认的纠偏放到最小适用范围，整理可复用模块与回归场景。未回复、继续聊天、只表扬一个片段，都不视为整轮批准。完成后才进入隔离模型/程序验证，使用合成会话，不污染用户聊天。

### 用户只需指出哪里不对，分类由助手做

用户可以直接说“第二个人太客服”“这句好”“她不该这么热情”“改成……”。助手保存原输入、人物与关系、原回答、用户原话、认可片段、适用范围、日期和测试 ID，再判断影响层：

| 反馈影响 | 放哪里 |
| --- | --- |
| 大多数人物都不能机械续聊等自然聊天问题 | 通用基座 |
| 慢热人物不应开局主动交底 | 相关行为模块；核对例外 |
| 仅此人物的口癖、价值观、经历 | 独立人物卡 |
| 某生活阶段的习惯或职业经验 | 有条件修饰/知识边界；不得推广全部同龄人或同行 |
| 只在当前关系/事件成立 | 场景或关系规则，不能写成人格常量 |

提升通用规则前用另一代表人物或新场景检查迁移范围。用户已明确给出的适用范围优先，不能把用户限定的单人纠偏自行推广。模块选择过程由助手处理，不把内部分类工作推给用户。

## 真正接到 App 前需要处理的缺口

本节来自 2026-10-04 对现有文件与调用链的只读核查，不表示已修复：

- 恢复项目缺全局 `zhiyu-dialogue` 2026-09-23 的路由、人物能动性、即时反应和粗语模块及相关来源闭环。需定向合并，不能整包覆盖，以免回退 Molly 新规则、现行人物姓名或 humanizer 路径。
- 普通人物生成/复核仍有跨角色整份注入夏夏/小满 40 条密度示范的路径。应迁移自然接话原则，相关已认可案例按人物与场景选取，防止人格同化。
- 旧公共粗语数值许可与 9/23 按人物/对象/语境判断冲突。新旧来源须保留，现行优先级必须明确，不能并行执行矛盾规则。
- 当前小满的显示名已为许晓曼，一些规则选择仍只认袁小满。规模化路由应以稳定角色 ID 与显式配置判断，不能依赖姓名字符串。
- 现有普通 NPC 的提示词、插件、会话接口/存储、Molly 目录仍有逐人注册。添加人物卡不等于自动创建可聊天联系人；配置驱动的人物注册属于后续程序工作。
- 生成、案例选择、成品复核要用相同人物/模块/关系上下文，并记录真正加载的规则版本。全局 Skill 更新、项目文件更新、App 加载和用户体验验收是不同状态。

## 当天完成标准

今天可以完成：确定复用结构；校准主要表达方向；交叉检查关键差异；把本聊天明确认可的改动沉淀成规则与案例；列清实际接入缺口。需要用户实际反馈的语感不能由助手自批通过。

这不等于今天逐人训练未来几千个 NPC、已经开通任意新增角色、已经完成模型微调，或未知人物效果全部获验收。后续成本应集中在新类型/例外和抽检，常规新人物用配置继承已校准基座。
