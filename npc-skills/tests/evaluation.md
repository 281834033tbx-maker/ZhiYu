# 如何检查没有改坏原有语感

## 状态与诚实边界

当前交付提供可执行的结构校验和53个待运行行为用例，不声称已经对实际模型、网页或冷却后台做了集成测试。明确获认可的台词只存在局部片段；没有“用户已验收整套对话”的golden集。

## 操作方式

1. 为每个用例建立干净角色/用户/分支夹具，传入用例指定的上下文、消息、可信时间及必要规则。多轮用例保持顺序，不泄漏其他测试的记忆。
2. 硬约束检查和语感评审分开。不要用逐字匹配代替自然度，也不要仅因台词不同就判失败。
3. 对冷却、回滚、去重等程序行为使用确定性状态断言。对“高冷”“自然”请用户盲评当前版与修改版，而非由同一个模型宣布自己通过。
4. 如需测试模型变化，固定同一组角色配置、关系、输入与模型设置，每个语感场景建议重复至少3次。次数是本包评估建议，不是用户已确认标准。
5. 发现回归时新增对照和适用范围，不通过“所有角色永远……”修补局部问题。

## 必须通过的行为检查

- 未明确确认的人物、参数和台词不冒称批准。
- 未看到的图片不编造细节；用户假设不变事实；角色换名不继承别人的状态。
- 冷却中角色消息数组为空；到期不自动清空负面记录。
- 授权回滚恢复完整分支，普通玩家不能用“暂停/重置”绕过运行规则。
- 低关系沈知遥不自动接梗、列全部爱好或长篇解释；开朗朋友不被同样规则压成冷淡角色。
- 改变消息条数不等于改变人格；普通交流、幽默和负面标签必须结合情境。
- 熟悉与亲密不同；高好感不代表必须恋爱；纯朋友路线不自动开启爱意。

## 人工语感评分表（建议）

每项0—2分：0明显不符；1可用但生硬；2自然且符合上下文。

| 维度 | 检查问题 |
|---|---|
| 接话自然 | 是在接这个人的话，还是自动提供服务和引导？ |
| 人格稳定 | 反应由这个人的偏好和状态产生吗，而非仅短句/表情表面特征？ |
| 节奏 | 想说才说，没话可停；有没有机械凑句、句句反问？ |
| 关系适配 | 初识/朋友/中等好感下的披露与边界是否合理？ |
| 记忆连续 | 是否核对已有事实、不凭空补写、不串分支？ |
| 后果一致 | 标签、数值、愿不愿回复是否相互支持，而不是嘴上说不悦却继续热情？ |

这是评估建议，不规定“12分就上线”。尤其T31需要用户选择方向，不能自动判定为批准。

## 结果记录建议

记录case_id、角色/规则/模型版本、输入、messages、action、前后状态、事件依据、人工评分、反馈、是否批准及批准范围。批准台词和批准原则分别存。不要把调试长解释当作需要玩家看见的回复。
